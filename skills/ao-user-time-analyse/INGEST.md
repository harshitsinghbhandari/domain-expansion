# AO human message export

Recover retained messages with their source and attribution evidence. Never claim an all time complete history: AO, providers, hosts, and Cloud have separate stores and deletion or retention may have removed records.

## Scope and authorization

Distinguish research from extraction. For research, inspect documentation, source, metadata, schemas, and bounded synthetic fixtures without reading private bodies. Before bulk extraction, get the user's explicit destination, format, host and Cloud scope, and authorization to read message content. Suggest `$HOME/ao/chats/user-messages.jsonl` as the private JSONL destination when the user has not chosen one, but confirm it before writing. A request to build a plan does not authorize an export. Do not alter sessions, daemon state, credentials, provider accounts, or remote access. Keep output private, avoid message text in terminal output, logs, reports, and chat, and do not publish it.

Use the current workspace and AO daemon. Discover the actual `AO_DATA_DIR` and database file instead of assuming a home path. The daemon database is `ao.db` under that data directory. Open SQLite with a read only URI (`file:<resolved path>?mode=ro`), use a read transaction, and discover the live schema with `PRAGMA table_info` before choosing columns. Do not copy or open a database in write mode merely to export. Prefer supported CLI and API reads first, then a read only database pass for retained records hidden from the visible UI.

## Inventory and supported reads

1. On each host, use `ao project ls --json` and `ao session ls --all --include-terminated --json` for a first inventory. The CLI addresses that host's daemon only. Check archived project and projectless session rows separately in the read only database; a normal project list omits archived registrations. Preserve host, project, session, and reviewer identities rather than treating an ID as globally unique.
2. For local Chat, page `ao session get <id> --transcript 500 --json`, using its `next.before` cursor as `--before`. `--cap 0` avoids text truncation. This covers the visible active branch of the local daemon. `ao session history <id> --offset 0 --limit 50` returns reduced completed Chat turns and retained Terminal UI turn summaries. It is not a complete transcript. The reviewer Chat route is `GET /api/v1/reviews/{reviewId}/conversation` with `limit` and `beforeSequence`. Conversation search finds visible matching words and is not an inventory or full export API.
3. For active side chats, list `GET /api/v1/sessions/{sessionId}/conversation/side-chats`, then page each side snapshot. Side transcripts live in daemon and Electron memory for one desktop launch, not in SQLite. Closed sides and sides retired with a launch are unavailable from AO.
4. For all retained local Chat facts, inspect `conversations`, `conversation_messages`, `conversation_turns`, `conversation_branches`, `review`, and `sessions` read only. Conversations can have session, project, or review scope. Project scope can span replacement orchestrators. The ordinary timeline query filters to the active branch and omits edited away, rolled back, cancelled, or some promoted inputs. Query the raw retained rows when the request includes those histories; label their visibility and turn state.
5. For Terminal UI, inspect `session_terminal_turns` and provider identity mappings in `sessions` and `agent_native_sessions`. AO keeps at most 50 Terminal UI turn summaries per session. A request submitted while a turn is open can be appended to that turn. Some hooks fail to report, and native provider transcripts may be missing or inaccessible. Treat native `role=user` as unverified because provider history can contain injected context. Never infer Harshit's authorship from a provider role alone.
6. Remote hosts require a separate authorized inventory and read against each host's own daemon. Cloud is a separate hosted control plane. For an accessible organization and session, its contract exposes paged `GET /api/cloud/v1/orgs/{orgId}/sessions/{sessionId}/chat-events?after=<sequence>&limit=500&types=chat.user_message`; `authorUserId` is useful actor evidence when it matches the authorized account. Archive retains Cloud event history according to the Cloud guide, but do not assume deleted or inaccessible records survive. Report unavailable hosts, organizations, profiles, and legacy stores as gaps. The legacy `ao import` ports projects and settings, not historical messages.

## Attribution and text safety

A local Chat `role=user, origin=human` row is an AO human-origin input, not verified proof of which person typed it. Check `sender_session_id`, session creation channel, and any available actor identity. `origin=automation` may include user authored relays, but the intake-only `AuthoredByUser` fact is not persisted on the message. Exclude or mark it unresolved unless independent evidence proves authorship. Keep `daemon`, `provider`, assistant, tool, worker report, handoff, and automated injection text out of the human authored set.

A Terminal UI hook row is a recorded user request with unverified actor. `sessions.prompt` may recover a missing opening prompt, but it has no durable author field and may contain agent or generated context. Include unmatched launch prompts only as explicit candidates, never as confirmed human messages. A provider native `role=user` record also needs independent attribution before export as human text. Avoid interpreting injected secrets or private context as the user's message.

Chat display text may differ from delivered provider input. Preserve whether `delivery_content_json` exists; do not blindly export embedded attachment payloads or assume text alone contains every attachment. CLI transcript output strips attachment payloads to metadata and separates a trailing `<ao-worker-reports>` block. Apply that split when reading raw rows and record that it happened. Keep attachment references or hashes only when needed and authorized.

## Reconciliation and JSONL

Use source row identity first for deduplication: host and database or Cloud scope, conversation ID, message ID, Terminal turn ID, or Cloud event sequence. Retain client message ID, provider item ID, branch ID, turn ID, native thread ID, and retry lineage for correlation. Never deduplicate by text alone. Compare imported Terminal turns with Chat rows and native records by session, thread, and turn before suppressing a duplicate. Preserve edits and retries as distinct events with lineage and visibility labels.

Sort by each conversation's immutable sequence within that conversation. Across conversations use recorded timestamps plus stable source IDs as deterministic ties, while noting that a session launch timestamp is not a send timestamp. Use UTF-8 JSONL with one object per record and at least `source`, `attribution`, `attribution_basis`, `host`, `project_id`, `session_id`, `created_at`, and `text`. For Chat add conversation scope and ID, message ID, sequence, branch ID, turn ID and state, origin, relevant delivery IDs, and structured-content and report-split flags. For Terminal use turn ID, harness, and native session ID when known. For launch candidates set `attribution=unverified_launch_prompt_candidate` and `timestamp_basis=session_created_at_not_send_time`. Null or absent fields must remain distinct from inferred values. Do not hardcode source counts or a personal destination from a prior run.

Write to a temporary file in the approved private destination, restrict the directory to owner access and the file to mode `0600`, validate every JSON line and record count without printing text, then atomically place it at the requested path. Do not overwrite an existing export silently. Report source counts, inaccessible sources, missing history, and attribution uncertainty separately from the file. A valid JSONL file proves the export ran, not that every message ever sent was recovered.
