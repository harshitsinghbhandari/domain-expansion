# AO user time analysis

Use retained AO messages to identify what the person asks agents to do, where their attention is repeatedly required, and which workflow changes could remove that work. Separate observed message activity from inferred time cost. Message timestamps do not measure active minutes, and incomplete history cannot support an all-time claim.

## Choose the starting point

If the user supplies a JSONL export, analyse that file. Do not rerun retrieval. If no export exists and the user asks for one, confirm the source scope, private destination, format, and permission to read message bodies before extracting. Suggest `$HOME/ao/chats/user-messages.jsonl` for JSONL if no destination was chosen. A request for a plan or skill does not authorize extraction. Do not overwrite an existing export silently, publish data, change live AO state, or access remote accounts or credentials without authorization.

For retrieval, inventory each local or authorized remote daemon separately with `ao project ls --json` and `ao session ls --all --include-terminated --json`. Normal project listing can omit archived registrations; include projectless sessions, workers, orchestrators, terminated rows, and reviewer conversations. `ao session get <id> --transcript 500 --json --cap 0` with `--before` pages visible local Chat. `ao session history <id> --offset 0 --limit 50` is a reduced turn view, not a full transcript. Active side chats have separate API snapshots and are process local; closed side chats are not durably retained. Remote hosts have separate daemons. Cloud has a separate event store and its own authorization; page `chat.user_message` events by sequence only for accessible organizations and sessions. Legacy `ao import` imports projects and settings, not messages.

For retained local rows outside the visible timeline, discover the actual `AO_DATA_DIR`, open its `ao.db` with a read only SQLite URI and transaction, and inspect the live schema with `PRAGMA table_info`. Use `conversations`, `conversation_messages`, `conversation_turns`, `conversation_branches`, `session_terminal_turns`, `agent_native_sessions`, `review`, and `sessions` as applicable. Project conversations may span replacement orchestrators. The active branch hides edited away, rolled back, cancelled, and some promoted inputs. Terminal UI hook summaries retain at most 50 turns per session and can combine queued prompts. Provider native transcripts can be missing or contain injected user-role context. Mark every unavailable source and retention gap. Do not claim every message ever sent was recovered.

## Classify authorship before analysis

Local `role=user, origin=human` means AO recorded human-origin input, not that a particular person is verified. Check sender session and actor metadata. Cloud `authorUserId` can identify a person when matched to the authorized account. An automation relay may carry user-written text, but its intake-only `AuthoredByUser` fact is not durable. Terminal hook requests have unverified actor. A session launch prompt can be human, agent, automation, or generated context; include it only as an `unverified_launch_prompt_candidate`. Native `role=user` also needs independent attribution. Exclude agent sends, worker reports, daemon and provider injections, assistant and tool messages from the confirmed human set. Use ambiguous records as context only, with a count and reason, rather than silently adding them to human metrics.

Preserve source identity, host, project, session, conversation scope, branch, turn, message or event ID, creation time, and attribution label in the export. Deduplicate by source identity and client or provider IDs, not by text. Keep edits and retries with lineage. Order within a conversation by immutable sequence; parse time zones for cross-conversation ordering and use IDs for ties. A launch time is not necessarily a send time. Record whether structured delivery content or attachments exist without dumping embedded payloads. Split a trailing `<ao-worker-reports>` block from human-visible text. Write approved JSONL through an atomic temporary file in a private directory, set file mode `0600`, validate every line and counts without printing message bodies, and report coverage gaps. Do not hardcode counts from a previous export.

## Analyse all eligible messages

Profile the entire file before interpreting it: record count, keys, source and attribution counts, projects, harnesses, states, date range, text length distribution, and missing timestamps. Read all eligible messages in bounded chunks, not a sample. Keep scratch data private and outside the repository. Separate directly typed or well-supported human messages from unverified launch prompts, Terminal summaries, and text that looks like an agent-generated relay. Prefixes such as `[from `, `<task-notification>`, and `Reports since` are clues, not proof; use sender and source fields first.

Build a chronological sequence per session. Identify initial asks, follow-up corrections, stop or retry nudges, status requests, handoffs, and repeated instructions. Rank request categories with approximate counts and a short representative example. For each recurring hands-off blocker, give dated evidence, affected sessions or public PR numbers when appropriate, the mechanism, and whether it is AO behavior, agent guidance, the user's rule, or a genuinely human-only approval or account action. Rank fixes by the number of messages they plausibly remove, favoring product and tool guards when the evidence supports them.

Report median message length, share of messages of 40 characters or less, messages and distinct sessions per month, and explicitly defined frustration or correction signals per month. If owner changes or PR cycles can be independently verified, report them; do not infer an owner change from a vague message. Estimate attention burden with message counts, correction episodes, and explicit durations the user stated. Do not convert gaps between messages into active work time or imply causation from a correlation. Label regex or subjective classifications approximate and state what is missing from a one-sided export.

## Private and shareable outputs

When the user requests the analysis, write a private report and a redacted shareable report beside the approved input or at the requested private destination. Use distinct filenames such as `user-analysis.private.md` and `user-analysis.shared.md`. The private report may contain short necessary quotes, dates, IDs, counts, ranked causes, and proposed fixes. Keep it skimmable. The shared report can keep aggregate patterns, mechanisms, fixes, and public AO PR or issue numbers, but paraphrase sensitive quotes and remove names and handles of other people, secrets and their identifiers, credentials, private tracker links or content, IPs and hostnames, local paths, emails, private repository or customer details, and personal, health, financial, or employment context.

Collect ambiguous sharing decisions in one concise question with the exact text, reason, and recommended keep, reword, or remove choice. Wait for the user's decision before finalizing the shared report, then record the decision in the private report. Scan the shared report for names, handles, emails, IPs, paths, private domains, credential terms, and sensitive context; fix every hit and rerun the scan. Do not send the input or either report to an external service or publish them unless the user separately authorizes it.

Use current CLI help and the generated API contract. If CodeGraph is available, use it for structural lookups; if its index is absent, ask before initializing it.
